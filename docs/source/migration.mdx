---
title: Migrating from Apollo Server 5
subtitle: Learn how to upgrade your Apollo Server 5 to Apollo Server 6 with minimal changes.
---

Apollo Server 6 is a small upgrade focused on the versions of Node.js and GraphQL.js that Apollo Server supports. This page tells you what to do to migrate your server from Apollo Server 5 to Apollo Server 6.

If you are still on Apollo Server 4 or Apollo Server 3, first follow the [migrating from Apollo Server 4](./migration-from-v4) or [migrating from Apollo Server 3](./migration-from-v3) guide to get to Apollo Server 5, then come back to this page.

We recommend that all users of [previous versions](./previous-versions) of Apollo Server upgrade to Apollo Server 6 as soon as possible. Apollo Server 5 will be end-of-life on INSERT-AS5-EOL-DATE. Apollo Server 4 has been end-of-life since January 26, 2026. Apollo Server 3 has been end-of-life since October 22, 2024. Apollo Server 2 has been end-of-life since October 22, 2023.

## Require Node.js v22

Apollo Server 6 supports Node.js v22.18.0 and later. (Apollo Server 5 supports Node.js v20.0.0 and later.)

If you're using Node.js v20 (or a v22 release older than v22.18.0), upgrade your runtime before upgrading to Apollo Server 6 to at least v22.18.0; we recommend upgrading all the way to the latest version. Node.js v20 has been end-of-life since April 30, 2026, so we recommend doing this even if you are not upgrading Apollo Server.

If your server requires you to use an [HTTP proxy](./security/proxy-configuration/) to make external connections, we strongly recommend running Node.js v24 or newer, which has built-in support for communicating through HTTP proxies.

If you can't upgrade to a non-EOL version of Node.js, you can continue to use Apollo Server 5.

### Node.js support policy

Starting with Apollo Server 6, Apollo Server's policy is that a *minor* release of Apollo Server may drop support for a Node.js major version once that Node.js version has reached end-of-life. Previously, Apollo Server only dropped support for Node.js versions in new Apollo Server major versions, which meant that Apollo Server 5 continued to support Node.js v20 for a year after it reached end-of-life.

Any such change will be called out in the changelog for the release that makes it. Apollo Server will not drop support for a Node.js version that is still supported by the Node.js project except in a new Apollo Server major version. This policy applies only to Node.js versions, not to other dependencies.

## Require GraphQL.js v17

Apollo Server 6 supports GraphQL.js v17.1.0 and later, as a peer dependency. (Apollo Server 5 supports GraphQL.js v16.11.0 and later.) Apollo Server 6 does not support GraphQL.js v16, so you must upgrade `graphql` and `@apollo/server` together, in a single `npm install`.

Before upgrading, read the [GraphQL.js v16 to v17 upgrade guide](https://www.graphql-js.org/upgrade-guides/v16-v17/) and check your own schema and resolver code for the changes it describes. The ones most likely to affect a server:

- The positional `GraphQLError` constructor is gone; pass an options object instead.
- `printError`, `formatError`, `getOperationRootType`, and `assertValidName` are removed.
- Resolver `args` and coerced input objects are null-prototype objects, so `args.hasOwnProperty(...)` no longer works (use `Object.hasOwn(args, ...)` or `'x' in args`).
- The parser may leave optional AST arrays `undefined` rather than `[]`, which affects custom validation rules and schema-directive code.
- `validateSchema()` now rejects invalid default values, so a schema that started under v16 can fail at startup under v17.
- The `reason` argument of `@deprecated` is non-null.

Every other package in your server that peer-depends on `graphql` must also accept v17, and most can be upgraded while you are still on Apollo Server 5. In particular, use `@apollo/subgraph` v2.16.0 or later and `@apollo/gateway` v2.14.5 or later.

GraphQL.js has a development-only check that detects when more than one copy of the `graphql` package is installed in your `node_modules`. Having two copies is a common mistake (typically caused by a dependency pinning a different `graphql` version), and without the check it shows up as confusing errors such as `Expected ... to be a GraphQL schema` or `Schema must contain uniquely named types`. With the check enabled, you get a clear `Cannot use GraphQLSchema "..." from another module or realm` error instead. In GraphQL.js v16, this check was on unless `NODE_ENV` was `production`. In v17, it is off by default and `NODE_ENV` is no longer consulted. To turn it on in development, call `enableDevMode()` (exported from `graphql`) before you build your schema, or run Node.js with `--conditions=development`, which makes Node.js load the development build of the `graphql` package.

## Incremental delivery changes

Apollo Server 4 and 5 supported the [incremental delivery directives `@defer` and `@stream`](./workflow/requests#incremental-delivery-experimental) only when combined with specific pre-release versions of GraphQL.js v17 (`17.0.0-alpha.2` in Apollo Server 4 and in Apollo Server 5.0, and `17.0.0-alpha.9` in Apollo Server 5.1 and later). Apollo Server 6 supports incremental delivery with any released version of GraphQL.js v17, with no special installation steps: define the `@defer` and `@stream` directives in your schema as described in the docs, and clients that send `accept: multipart/mixed; incrementalSpec=v0.2` receive streaming responses.

Apollo Server 6 no longer supports the older response format that clients request with `accept: multipart/mixed; deferSpec=20220824` (the only format supported by Apollo Server 4 and 5.0, and available in Apollo Server 5.2 and later via the `legacyExperimentalExecuteIncrementally` option). Operations that use `@defer` or `@stream` from clients that send only that `accept` header now receive a `406 Not Acceptable` error. The `legacyExperimentalExecuteIncrementally` constructor option has been removed.

If you write plugins or integrations that process incremental responses, note that the `GraphQLExperimental*Alpha2` and `GraphQLExperimental*Alpha9` types that `@apollo/server` exported (such as `GraphQLExperimentalFormattedSubsequentIncrementalExecutionResultAlpha9`) have been removed. `GraphQLResponseBody` and the `willSendSubsequentPayload` plugin hook now use the `FormattedInitialIncrementalExecutionResult` and `FormattedSubsequentIncrementalExecutionResult` types exported from `graphql` instead, which have the same shape as the removed `Alpha9` types.

## Remove `status400ForVariableCoercionErrors`

Apollo Server 4 had a regression where operations with invalid variables (for example, a string provided for an `Int!` variable) received a 200 status code instead of 400. Apollo Server 5 fixed this by defaulting the `status400ForVariableCoercionErrors` constructor option to `true`, and deprecated setting it to `false`. Apollo Server 6 removes the option: variable coercion errors always receive a 400 status code. If you pass this option to the `ApolloServer` constructor, remove it.

## New: request cancellation signal

`HTTPGraphQLRequest` has a new optional `signal` field. Integrations that provide an `AbortSignal` and abort it when the client disconnects let Apollo Server stop execution early: GraphQL.js exposes the signal to resolvers via `info.getAbortSignal()`, and an operation whose signal fires before execution completes ends with a `REQUEST_ABORTED` error instead of running to completion. The standalone server (`startStandaloneServer`) does this automatically. This is optional for integrations; nothing changes for integrations that don't set it.

## `@cacheControl` definition is checked, and `scope` is required

If your schema defines the `@cacheControl` directive (which you need in order to use it in your SDL), the cache control plugin now checks on startup that the definition matches the documented one, and the documented definition now declares `scope` as non-null:

```graphql
enum CacheControlScope {
  PUBLIC
  PRIVATE
}

directive @cacheControl(
  maxAge: Int
  scope: CacheControlScope!
  inheritMaxAge: Boolean
) on FIELD_DEFINITION | OBJECT | INTERFACE | UNION
```

Previously, `scope` was nullable and defaulted to `PUBLIC`, so a field annotated with just `@cacheControl(maxAge: 60)` was cacheable by shared caches and CDNs, which is easy to do by accident. With a non-null `scope`, GraphQL.js's own SDL validation rejects every `@cacheControl` usage that doesn't say `scope: PUBLIC` or `scope: PRIVATE`, including `@cacheControl(inheritMaxAge: true)`.

To migrate, change `scope: CacheControlScope` to `scope: CacheControlScope!` in your definition, and add `scope: PUBLIC` (or `PRIVATE`) to every `@cacheControl` usage. The startup error prints the expected definition. If you want to keep the old definition for now, pass `validateDirectiveDefinition: false` to `ApolloServerPluginCacheControl`. Cache hints set from code (`info.cacheControl.setCacheHint({ maxAge })`, `defaultMaxAge`) still default to `PUBLIC`.
